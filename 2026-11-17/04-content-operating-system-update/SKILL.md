# Content operating system update (2026-11-17)

This update extends the content operating system pack (2026-09-01/07-content-operating-system, first shipped 2026-08-18). It adds three things the original left out: pipeline edits, an animation method, and a shared library of motion moves. The original files stay as they are. Read the original first, then read this.

Who this is for: an operator who has already built the content system and wants better checks and better video.

## 1. Pipeline edits

The original pipeline moves an item from evidence to ideas to a finished asset. This update adds checks at each step.

**Code every item as it arrives.** Do not wait for the weekly batch. When a piece of evidence lands, tag it with six codes, each with a confidence score:

- Audience: who it is for
- Pain: the problem they feel, in their own words
- Offer: what you put in front
- Format: how it is shown
- Awareness: how much they already know
- Angle: the one way in this piece uses

A code with low confidence is marked as a guess. The queue shows the guess, so nobody mistakes it for a fact.

**A model picks, code decides.** Use a language model only for a closed choice: yes or no, or pick one from a fixed list. Screen the text before the model reads it, and drop anything aimed at the model. If the answer is not on the list, throw it away. What happens next is a rule in code. The screen shows only lines you wrote.

This sharpens the original rule that a model call is for judgement. Counting, sorting, filing and ranking stay in code.

**Each batch declares what it demonstrates.** Before a batch is built, write one line that says what it shows. Example: "This batch shows that the price objection gets answered on camera." The batch gate checks each asset against that line, as well as the mechanics the original gate checked: traceability, banned words, format, and files that exist.

**Nothing is finalised until the gate exits clean.** A batch that has not passed the gate is not finished, handed over or imported anywhere. "It looks finished" does not count.

**Two kinds of check, kept apart.**

- Hard checks block. They test facts and rules: banned words, missing sources, missing files, a wrong format.
- Judgement checks advise. They test craft: whether each beat earns its place, and whether the script still works if one element is swapped. They report and never stop a batch. The person decides.

**Argument audit.** For each script, ask of every beat whether it earns its place. A beat that does not is cut or rewritten before a person sees it.

**Every exception is written down.** A check can be broken on purpose, but only with a written reason. An exception without a reason does not count. The check still prints the finding, marked as excused.

**Reviewed work is fingerprinted.** When a person reviews an item, record a fingerprint of its brief, sources and output. If any of those change afterwards, the item goes back to the start of review. Otherwise a reviewed item could be swapped for a different one without anyone noticing.

**One review place.** Review scripts, videos and carousels in one app, item by item, with feedback on any frame. Re-render only the part that changed, not the whole film.

## 2. Animation philosophy

Animation moves through five stages. Each stage must clear before the next one starts. Build authority comes from watching a reference, not from building first and justifying later.

1. **Brief.** Name the beat, the audience, the evidence, the format, the frame shape and the length. Nothing is left to default.
2. **Reference.** Choose the approved piece whose movement you will inherit, and watch it. Picking it off a list does not count as watching.
3. **Build authority.** Write what you saw under five fixed headings: Composition, Camera, Identity, Evidence match, Anti-pattern. An empty heading means no build.
4. **Candidate evidence.** Render the piece. Save a contact sheet of three frames, and a probe that reads the real width, height and length. Check both against the brief.
5. **Delivery.** An independent critic returns a verdict, and the batch gate must exit clean.

**Reference by mechanism.** Name the movement, not the look. Examples of mechanisms: scattered pieces collapse into one system, one request travels through real stages, one action fans out into a result. A new piece may combine at most two mechanisms, and it must say which it inherits from. A new idea that cannot name its parent is decoration.

**A visual banlist is a hard fail.** Keep a short list of looks and props that fail on sight. Examples: neon and glow lighting, coloured shadows, glass cards floating in an empty void, fake receipts, invoices and clipboards, and invented dashboards or metrics. A real dashboard is allowed only when the real product and the real state call for it. A banlist hit forces a reject, whatever the scores say.

**Motion explains. It never decorates.** Every move must show a cause, a replacement, a change of scale, a change of place or a change of state. Fades, scaling or sparkles with no cause are faults. A slow zoom as the only idea is a fault.

**Type restates nothing.** Screen type carries only what the picture is about: a real figure, the name of a real tool, a short label. A narrated sentence set as a graphic says the same thing twice. When a beat feels empty, change the picture, not the words.

**Every piece ends on a clean hold.** Hold the last frame for twenty to thirty frames, so an editor can cut anywhere.

**The blind critic.** The maker cannot grade their own work. A fresh reader gets only the brief, the evidence, the reference and the render. It never sees the maker's explanation. It scores eight axes from 0 to 10:

- Evidence fidelity: every figure traces to a real record
- Reference fidelity: the cited mechanism is visible
- Concept specificity: the piece could only belong to this beat
- Authenticity: real tools, real surfaces, no invented proof
- Mobile readability: the action and the type survive a phone screen
- Composition: clear scale, hierarchy and end state
- Motion causality: every move has a cause
- Material restraint: nothing on the banlist

The threshold used in the original build: every axis at 8 or above, an average of 8.5 or above, and no hard fail. Adjust the numbers to your own bar, but keep the rule that the critic is independent. If no independent critic can run, the piece stops there. Self-approval is never a fallback.

## 3. Universal moves

A move is one named way something moves, enters, exits, changes or appears on screen. Examples: a slow push, a wipe, a count-up, a cut on a beat, a caption that holds.

**The shared library.** Keep one list of moves that every format can reuse. Each entry records:

- its name and its family (a group of similar moves, such as reveal or transition)
- the beats it suits, such as a list, a number, a comparison or a question
- its status: approved, unreviewed, rejected or reference only
- the code that makes it
- a short quote from the note that records it

One working library held 635 moves across 64 families. A query returns the moves that fit the line being said, with their status beside them.

**Build a move once.** A shared move lives in one place. A format uses the shared move first, and its own rules still win inside its own format. Never edit a shared move to suit one format. Make a new move instead.

**Every move has a card.** The card says what the move is for, what it is for not, when to use it, when to avoid it, what it grew from, and what it does that the closest move cannot. A missing or vague card fails the check.

**Reskin check.** A new move that repeats an old one in a new look is refused. Compare the movement, not the colour.

**The library is add-only.** Indexing existing formats never changes how they render. Each format keeps its own working rules.

**A build check guards every pointer.** The check fails when a move names a code file that does not exist, or a quote that cannot be found word for word in its note. Nothing unchecked goes into the library.

### How to start one

1. Put one shared renderer and one clock under every format, so all of them share the same timing.
2. Create the family list. Start with the smallest set that describes the moves you have.
3. Pick one format. Watch its approved pieces and list each move it uses.
4. Write one entry per move, with its family, beats, code and quote.
5. Write a card for each move.
6. Run the build check. A format counts as codified only after the check passes.

### How a new format adds its moves

1. Query the library for the beats in the new script.
2. Reuse every shared move that fits.
3. Build only the missing moves, one at a time.
4. Create a new family only when no existing family describes the move. Never rename a family.
5. Save the new format's list in its own file, then run the build check.

## Writing rules

Plain English, short sentences. No em dashes. Never write "it's not X, it's Y". 
Never use: delve, leverage, unlock, seamless, game-changer, robust, elevate.
